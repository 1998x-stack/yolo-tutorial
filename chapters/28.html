CAPSTONE / ACCEPTANCE ／ CHAPTER 28

综合实训：一次可验收的检测项目

一个项目是否完成，不取决于它讲过什么，而取决于每一步留下了什么可复核的产物。本章给出一条带门槛的端到端流程与交付清单。

1. 先用契约定义“完成”

一个可验收的项目在开工前就写清了验收条件，否则“做完了”只是主观判断。契约至少要回答：检几类、每类边界如何定义；用哪个划分与哪个指标验收；在什么设备与输入尺寸下达到什么延迟；两类错误各自的后采代价与可接受范围。这些参数一旦写入，后续所有改动都要与它对比。

以“桌面物品检测”为例，一个可验收的契约形如：7 类常见物品；输入为手机拍摄的桌面图像；在指定的验证/测试划分上报告 COCO AP 与 AP@0.5（两者分开写）；在目标设备上报告 p95 端到端延迟；错误按漏检与误报分开统计。具体的数值阈值由项目方设定，不能由算法人员自行粉饰。

2. 数据门槛：先过检查再审模型

数据阶段的产物不是“一堆图片”，而是一份可复核的数据集：图像与标签目录镜像、一份固定的划分清单、一份数据字典（类别名与 id 的对应）以及一份校验报告。采集覆盖度应先定义再执行：不同背景、不同光照、不同拍摄设备与距离、不同摆放与遮挡程度。覆盖度不够时，再好的模型也无法泛化。

校验至少包含：标签与图像一一对应（无用标签、无漏图像）；每行字段合法；类别 id 在范围内；归一化坐标在约定范围内；换算回像素后面积大于零。划分必须先于任何增强或切片，且连续帧、同一场景的样本不得跨划分。完成后再统计类别频率、目标尺度与宽高比分布，判断验证集是否能代表部署分布。

这些规则不是建议，而是门槛：校验报告不过，就不要进入训练阶段。否则你会在 loss 曲线里花大量时间排查一个本质上是数据的问题。

3. 基线对照：一次只动一个旋钮

训练阶段的第一产物是基线：一个用最小模型与固定配置跑出的、可复现的结果。它的作用是给出参照点，而不是终点。基线阶段就要把配置（模型结构、输入尺寸、epoch、增强、优化器、种子、硬件与库版本）写入实验记录，以后每次对比都以此为基准。

迭代时遵循单一变量：先看数据（补充哪类样本、修正哪类标注），再看输入（分辨率、增强强度），最后才是模型容量与超参。模型容量几乎总能提高拟合能力，却也增加延迟；在契约规定的延迟预算内选择最小可行模型，通常比追求最大模型更符合工程目标。

# 基线训练的最小入口（选项与默认值以所用版本文档为准）
from ultralytics import YOLO
model = YOLO("yolo11n.pt")
model.train(data="desktop.yaml", epochs=100, imgsz=640, batch=16, seed=0)

# 训练前先过数据校验（参见第 23 章的检查项），并把生效配置存档
metrics = model.val(data="desktop.yaml", split="val")

注意：不要把验证集当成训练信号反复调参。每次改动都应在同一验证划分上比较，而测试划分在定稿前不参与任何决策。

4. 迭代与不确定性：分清“真的提升了”与“噪声”

迭代的依据是错误分解，而不是随机换参。先把错误按定位、分类、背景误检与重复检测分类统计（口径参见第 25 章），再把错误与样本属性（尺度、密度、光照）交叉，找出被平均值掩盖的模式。每次只针对一个模式改动并做受控对比。

对比时要估计指标本身的抽样不确定性。验证集很小的时候，一两个样本就能拉动指标。若把单类比例 p 看作二项比例，其估计的标准误为：

SE=p(1-p)n

其中 n 为用于估计的样本数。它说明：验证集越小，指标波动越大，小幅“提升”可能只是噪声。下面是固定 p=0.9 时的标准误：

固定 p=0.9（教学示意），拖动样本量 n，按 SE = √(p(1−p)/n) 估算标准误；它提醒你指标差异是否值得当真。

5. 导出与交付：接口和双验收

交付阶段要同时验收两件事：任务质量（在固定划分上的指标）与运行指标（目标设备上的 p95 延迟、峰值内存/显存与持续帧率）。两者分属不同口径，不能用一个代替另一个。导出时应记录后端、精度、输入尺寸与动态维度设置，并用同一批输入比较原模型与导出模型的输出差异。

除模型文件，交付物还包括接口契约：输入张量的形状、通道顺序、颜色空间、归一化方式、尺寸变换（letterbox 的填充与缩放因子）、输出结构（框、分数、类别、可选掩码/ID）以及坐标所处的参考系。接口不清会导致上游预处理与下游解码错位，表现为“模型明明很准，集成后却全错”。成熟做法是把预处理与后处理参数一并版本化，并写一个用固定输入验证全链路的冒烟测试。

6. 交付清单：拿什么证明项目完成

下表把前文各阶段的门槛汇总为一份可勾选的交付清单。每一项都对应一个可被第三方复核的物件，而不是描述性的结论。

交付物内容验收方式
数据集与划分images/labels 镜像目录、固定划分清单、数据字典校验脚本零错误；划分不跨场景泄漏
生效配置模型结构、超参、数据、种子、库与驱动版本重新跑一遍能得到容差内一致的结果
基线对照记录每次改动的单一变量与同划分指标改动可归因，不能叠加多项后归功于一项
评估报告指标口径 + 划分 + 分类别/分尺寸 + 错误分解AP@0.5 与 COCO AP 分开报告，不混用
导出模型ONNX/engine 等目标格式与精度、维度设置与原模型输出差异在容差内
接口契约预处理/后处理参数、张量约定、坐标参考系固定输入的端到端冒烟测试通过
运行指标目标设备上的 p95 延迟、吞吐与峰值内存热平衡后测得，口径写清

这份清单同时也是自检手册：任何一项缺失，项目就还没真正完成。把它与第 27 章的任务契约结合，就得到一条从需求到验收的完整链条。

一手来源与复核边界

  1. COCO 检测评估指标：核对 AP 与 AP@0.50:0.95 的官方定义，用于本文的验收口径。
  2. Ultralytics 训练文档：核对训练/验证入口与配置项。
  3. Ultralytics 导出文档：核对导出格式与精度选项。
  4. PyTorch 可复现性说明：核对种子与硬件差异导致的复现边界。
  5. Microsoft COCO 原论文（ECCV 2014）：核对评估协议的原始描述。
