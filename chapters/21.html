部署与推理加速：导出、后端与基准口径

把推理加速拆成导出、图优化、精度校准与基准测试四个环节，说明每个环节能改变什么、不能改变什么。

1. “加速”要优化的到底是哪个指标？

部署语境里被笼统称为“延迟”的量至少包含三组互不相同的指标：单帧延迟（从输入到输出，通常报告 p50/p95 而不是平均值）、批量吞吐（单位时间处理的帧数）以及峰值内存/显存占用。三者经常互相冲突：把 batch 调大通常提高吞吐，却抬高单帧延迟；把输入分辨率调低降低计算量，却可能损失小目标精度。

更关键的是，模型前向只是整条流水线的一段。目标检测的端到端时间通常还要计入图像解码、letterbox 缩放、归一化、张量搬运、坐标解码、置信度筛选与 NMS。这些后处理大多运行在 CPU 上，只测量 GPU 前向内核会把真正的瓶颈藏起来。

因此一个可复核的优化目标必须写成带约束的形式，例如“在同一设备、同一输入分辨率下，使 640×640 输入的 p95 端到端延迟低于某阈值，同时验证集 COCO AP 相对 FP32 基线的下降不超过事先约定的量”。缺少设备、精度口径和基线参照的“快 N 倍”无法比较。

2. 导出流水线：为什么中间要经过 ONNX？

训练框架（如 PyTorch）保存的权重面向动态图：前向计算在运行 Python 时才被逐条记录，便于调试却带来运行时开销。生产推理更希望得到一个静态计算图——算子、数据流与张量形状在运行前就确定，从而允许常量折叠、算子融合与内存规划。

ONNX（Open Neural Network Exchange）正是这个静态图的中间表示：它把模型表示为有向无环图，节点是算子（Conv、Add、Resize…），边是张量。它用版本化的算子集（opset）规范算子语义，不同后端只要支持同一 opset，就能读取同一份模型，因此它常被当作格式转换的“中间站”。

YOLO 官方工具链提供统一的导出入口，用 format 选择目标后端，用 half/int8 选择精度、dynamic 控制是否保留动态维度（命令与默认值会随版本变化）：

# 导出为不同后端的目标格式（Ultralytics 导出接口，具体选项随版本变化）
yolo export model=yolo11n.pt format=onnx            # FP32 ONNX
yolo export model=yolo11n.pt format=onnx half=True   # FP16 ONNX
yolo export model=yolo11n.pt format=engine           # TensorRT 引擎
yolo export model=yolo11n.pt format=openvino         # OpenVINO IR
yolo export model=yolo11n.pt format=coreml           # Apple CoreML

导出不是无损复制。转成静态图时必须把控制流、动态形状和自定义算子表达为目标格式支持的算子；不被支持的算子会被拆解、替换，甚至回退到 CPU。因此导出后应当用同一批输入比较原模型与导出模型的输出差异，而不是只看文件能否加载。

3. 图优化：融合、折叠与内存复用

拿到静态图后，推理后端会执行几类与硬件无关或半无关的图级优化。它们改变的是图结构，而不是数值本身，通常在保持数值等价的前提下减少开销。

  • 常量折叠：把只依赖常量输入的子树在构建期算完，直接写入结果。
  • 算子融合：把连续的 Conv → BatchNorm → 激活合并为一个内核，减少内核启动次数与中间张量的显存读写；BN 在推理期可以折叠为卷积的缩放与偏置。
  • 内存复用：分析各张量的生命周期，让不重叠的张量共用同一块显存，压低峰值占用。
  • 内核自动调优：对同一算子尝试不同的 tile、分块与并行策略，在目标设备上挑选较快实现。

这些优化“等价”需要验证：先用一组固定随机输入比较优化前后的最大绝对误差，再在目标设备上测量真实延迟。同一算子在某个后端可能落到不同实现，数值结果与速度都会随之改变，两者都要单独记录。

4. 精度：FP16 降位宽，INT8 先标定

FP16 把权重与激活从 16/32 位浮点降为半精度，通常只需在导出时声明，不需要额外数据。它的数值范围足够宽，但对极小/极大的激活仍可能溢出或下溢。INT8 则把连续值映射到 8 位整数，必须为每个（或每组）张量确定缩放因子与零点，这个过程称为校准。

常见的仿射量化把浮点值 x 映射为整数：

q=clamp(round(xS)+Z,qmin,qmax)

其中 S 通常由校准数据的激活范围估计，Z 是整数零点。这里存在两层彼此独立的误差：参数存储只决定文件字节数，而运行时是否是整数运算取决于后端是否为该算子匹配了量化内核。若某层未被量化，它会插入反量化/量化节点，既增加访存又不能带来相应加速，因此不能由“权重文件缩小到四分之一”推断延迟也变成四分之一。

后训练量化（PTQ）用一批有代表性的图片估计激活范围；量化感知训练（QAT）则在训练中模拟量化误差。校准集必须贴近部署分布，否则激活范围估计会偏离实际推流。量化后还应分别检查分尺寸 AP、类别混淆与长尾样本，而不仅是整体 AP。

5. 基准测试协议：让数字可以被别人重算

一个可信的延迟/吞吐报告需要交代：设备型号与驱动、输入分辨率与 batch、浮点精度与推理后端版本、是否包含预处理与后处理、预热次数与重复次数、以及报告的是均值还是 p95。缺少任何一项，“快了几倍”都不可复现。

延迟与吞吐不是倒数关系。设单次调用含固定开销 a 与每帧成本 c，batch 为 b 时，单次延迟约 a+b·c，吞吐则为 b 除以该延迟。增大 batch 会提高吞吐，但单帧延迟也随之上升：

教学参数：固定开销 5 ms、每帧成本 2.5 ms，仅前向、不含预处理与后处理。拖动 batch，观察吞吐与单帧延迟如何同时变化（单位为教学示意值）。

报告时还应区分构建时间与运行时间：图优化与内核调优发生在引擎构建阶段，一次构建可多次加载，把它计入首帧延迟会误导在线服务的容量规划。同一模型的多次导出（不同 opset、不同动态形状）会得到不同的引擎，因此“某模型在某 GPU 上的延迟”必须绑定到具体的引擎与配置。

6. 一手来源与复核边界

  1. Ultralytics 模型导出文档：核对 format、half、int8、dynamic 等导出选项及其随版本的变化。
  2. ONNX IR 规范：核对计算图、算子集（opset）版本与张量形状的静态表示。
  3. ONNX Runtime Execution Providers：核对同一 ONNX 模型在不同硬件后端上的落地方式。
  4. NVIDIA TensorRT Developer Guide：核对层融合、INT8 校准与引擎构建流程。
  5. OpenVINO 文档：核对 IR 转换、shape 重设与设备插件。
  6. 量化方法综述（Gholami et al., 2021）：核对仿射量化、校准与量化感知训练的术语边界。
